# 第1話　月曜の朝、「先月の1件を直して」と言われた

::: tip この話で分かること
- 今のデータレイク（S3にParquetを置く方式）で、たった1行を直すだけでも何が大変なのか
- その途中で、なぜ「売上が倍になったレポート」が出てしまうのか
:::

## 登場人物と舞台

あなたは、架空の小売チェーン「ミドリマート」のデータ基盤担当です。

- 全国200店舗の売上データが、毎晩S3に届きます。
- 形式はParquetで、日付ごとのフォルダに置いています（`dt=2026-09-01/` のように）。
- 分析チームはこのフォルダをDuckDBやAthenaで読み、経理チームは毎朝、日別の売上合計レポートを見ています。

もう2年、この形で問題なく回ってきました。

## 月曜の朝

経理から、こんな依頼が届きます。

> 「9月1日分の注文 #3 の金額が、400円になっていますが、正しくは999円でした。レポートを直してください」

たった1行の訂正です。SQLのDBなら `UPDATE sales SET amount = 999 WHERE order_id = 3;` で終わる話です。

## いまの基盤を再現してみる

この教材はDuckDBだけで動きます。クラウドも課金も要りません。

```bash
mkdir -p lake   # DuckDBは親ディレクトリを自動では作らないので、先に作ります
duckdb <<'EOF'
CREATE TABLE sales AS
SELECT i AS order_id,
       DATE '2026-09-01' + CAST(i % 3 AS INTEGER) AS dt,
       'item_' || CAST(i % 5 AS VARCHAR) AS item,
       (i % 7 + 1) * 100 AS amount
FROM range(1, 10001) t(i);
COPY sales TO 'lake/sales' (FORMAT parquet, PARTITION_BY (dt));
EOF
find lake -type f | sort
```

`dt` ごとのフォルダにParquetファイルが1つずつできます。これが、ミドリマートの「salesテーブル」の実体のすべてです。

9月1日の合計を確認しておきます。

```bash
P=lake/sales/dt=2026-09-01
Q="SELECT count(*) AS rows, sum(amount) AS total
   FROM read_parquet('lake/sales/*/*.parquet', hive_partitioning=true)
   WHERE dt='2026-09-01'"
duckdb -c "$Q"
```

この環境では `rows=3333, total=1333200` でした。

## 「1行だけ直す」ことはできない

`UPDATE` を書こうとして、気づきます。**Parquetファイルは、一度書いたら中身を書き換えられません。**

できることは、その日のファイルを丸ごと読み込み、1行だけ値を変えて、**新しいファイルとして書き出す**ことだけです。3333行の中の1行のために、3333行を書き直します。

```bash
duckdb -c "COPY (
  SELECT order_id, item, CASE WHEN order_id=3 THEN 999 ELSE amount END AS amount
  FROM read_parquet('$P/data_0.parquet')
) TO '$P/data_1.parquet' (FORMAT parquet);"
```

新しいファイル `data_1.parquet` ができました。あとは古い `data_0.parquet` を消せば完了です。……その前に、いま読んだらどうなるのか、確かめてみます。

## 古いファイルを消す前に、誰かが読んだら

```bash
ls $P
duckdb -c "$Q"
```

| 状態 | フォルダの中身 | rows | total |
|---|---|---|---|
| 更新前 | data_0 | 3333 | 1333200 |
| **新ファイルを書いた直後** | **data_0 と data_1** | **6666** | **2666999** |

行数が6666、合計が約2倍になりました。フォルダには「古い版」と「新しい版」の両方があり、読む側は**フォルダの中身をそのまま全部読む**ので、同じ日のデータを二重に数えてしまうのです。

もしこの瞬間に、経理の朝のレポートが走ったら。「9月1日の売上が突然2倍になった」と、経営会議に出てしまうかもしれません。

では、古いファイルを消します。

```bash
rm $P/data_0.parquet
duckdb -c "$Q"
```

結果は `rows=3333, total=1333799` です。`400 → 999` の差分 `+599` が、正しく反映されました。

::: warning ここが怖いところ
「新しいファイルを書く」と「古いファイルを消す」は2つの別々の操作です。**その2つを、同時に、ひとまとめにする手段がフォルダにはありません。**
今回はローカルで、一瞬でした。本番のオブジェクトストレージで、ファイルが大きく、書き込みに数分かかるなら、二重に見える時間もその分だけ長くなります。
:::

## ここで、こう思いませんか？

::: details 💬 「消してから書けばいいのでは？」
先に古いファイルを消して、あとで新しいファイルを書くなら、今度は**その間、データが消えて見えます**（合計が0や欠けた値になる）。どちらの順番でも、途中の状態が読み手に見えることは避けられません。
:::

::: details 💬 「ロックをかければいいのでは？」
フォルダ（オブジェクトストレージ）には、DBのような「書き込み中は読ませない」仕組みがありません。読み手側のツール（DuckDB、Athena、Spark…）が全部それを守るように、自分たちで運用ルールを作る必要があります。
:::

::: details 💬 「そもそもパーティションを丸ごと入れ替えればいいのでは？」
実際にそうやって運用している現場は多いです。ただ、上の問題は残りますし、1行のために毎回1日分を書き直すコストもかかります。
:::

## 第1話のまとめ

- Parquetは書き換えられないので、1行を直すだけでもファイルごと書き直しになる
- 「新しいファイルを書く」と「古いファイルを消す」の間、読み手には二重（または欠け）が見える
- フォルダには、それをひとまとめに切り替える手段がない

## 確認していないこと

- この現象は、ローカルのファイルとDuckDBで再現したものです。S3やADLS2上で、ファイル数が数十万になったときの一覧取得の遅さなどは、この話では確認していません。
