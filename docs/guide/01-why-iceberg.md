# 1. なぜIcebergか

::: tip この章のゴール
- 従来のデータレイクが「フォルダ＝テーブル」だったことと、そのせいで何が困るのかを説明できる
- 「Icebergは、テーブルの定義を変えることでそれを解決した」と一言で言える
- Icebergを選ぶ場面・選ばない場面の判断材料を持つ
:::

## 1.1 従来のデータレイクは「フォルダ＝テーブル」だった

S3 / ADLS2 / GCS などのオブジェクトストレージにParquetファイルを置き、Hive形式のフォルダ構成でパーティションを表現する。これが従来のデータレイクの基本形です。

```
lake/sales/
├── dt=2026-09-01/data_0.parquet
├── dt=2026-09-02/data_0.parquet
└── dt=2026-09-03/data_0.parquet
```

このとき、**テーブルの実体は「フォルダの中身」そのもの**です。「salesテーブルにどんな行があるか」は、フォルダを`ls`して、見つかったファイルを全部読むことで決まります。

一見シンプルで、実際にこの方式で長く運用されてきました。ただ、テーブルの定義を「フォルダの中身」に預けているせいで、次の問題が構造的に避けられません。

## 1.2 無かったらどう困るか（フォルダ＝テーブルの限界）

### ① 1行を直すだけでも、ファイルごと書き直しになる

Parquetは一度書いたら中身を書き換えられないファイル形式です。`order_id=3`の金額を1行だけ直したくても、その行が入っているパーティションのファイルを丸ごと読み直して、新しいファイルとして書き直すしかありません。

### ② 書き込み途中の状態が、読み手に見えてしまう

書き直しは「新しいファイルを書く → 古いファイルを消す」の2手順です。フォルダは全体を一度に切り替える手段を持たないので、その途中で読まれると**古い版と新しい版の両方が見えて、データが二重になります**（次の節で実際に確認します）。

### ③ ファイルが増えるほど、`ls`自体が遅くなる

「どのファイルがテーブルに含まれるか」を知るには、フォルダの一覧取得が必要です。オブジェクトストレージの一覧取得は、1回のAPI呼び出しで返せる件数に上限があり、ファイルが数十万・数百万になると、クエリを始める前の一覧取得だけで時間がかかります。

### ④ スキーマ変更が、読み手との解釈のずれを生む

列の追加・改名・型変更をすると、すでに書かれた古いファイルと、新しい定義を前提にした読み手の間で、列の解釈がずれる場面が出ます。定義がファイル側にしか無く、テーブル全体としての「今の正しい定義」を持つ場所が無いためです。

### ⑤ パーティションが「フォルダ名の約束事」でしかない

パーティション列が`dt=...`というフォルダ名の規則として表現されているので、クエリを書く人が「このテーブルは`dt`で分かれている」と知っていて、条件に`dt`を書かないと全件読みになります。あとからパーティションの切り方を変えたくなった場合も、全データを新しいフォルダ構成に書き直す必要があります。

## 1.3 手を動かして確かめる：①と②を再現する

::: warning 環境
DuckDB（CLI）だけで動きます。クラウドや課金は不要です。ファイルは作業ディレクトリの`lake/`以下にできます。
:::

### 「フォルダ＝テーブル」を作る

```bash
mkdir -p lake   # DuckDBは親ディレクトリを自動では作らないので、先に作ります
duckdb <<'EOF'
CREATE TABLE sales AS
SELECT i AS order_id,
       DATE '2026-09-01' + CAST(i % 3 AS INTEGER) AS dt,
       'item_' || CAST(i % 5 AS VARCHAR) AS item,
       (i % 7 + 1) * 100 AS amount
FROM range(1, 10001) t(i);
COPY sales TO 'lake/sales' (FORMAT parquet, PARTITION_BY (dt));
EOF
find lake -type f | sort
```

`dt`ごとのフォルダに、Parquetファイルが1つずつできます。これが「テーブルの実体」のすべてです。

### 2026-09-01の合計を確認する

```bash
P=lake/sales/dt=2026-09-01
Q="SELECT count(*) AS rows, sum(amount) AS total
   FROM read_parquet('lake/sales/*/*.parquet', hive_partitioning=true)
   WHERE dt='2026-09-01'"
duckdb -c "$Q"
```

この環境での結果は `rows=3333, total=1333200` でした。

### `order_id=3`の金額（400）を999に直す

Parquetは書き換えられないので、パーティションのファイルを読み込んで、1行だけ値を変えた**新しいファイルを書き出し**ます。

```bash
duckdb -c "COPY (
  SELECT order_id, item, CASE WHEN order_id=3 THEN 999 ELSE amount END AS amount
  FROM read_parquet('$P/data_0.parquet')
) TO '$P/data_1.parquet' (FORMAT parquet);"
```

### ここで、古いファイルを消す前に読んでみる

```bash
ls $P
duckdb -c "$Q"
```

### 旧ファイルを消して、もう一度読む

```bash
rm $P/data_0.parquet
duckdb -c "$Q"
```

### 結果のまとめ

| 状態 | ファイル | rows | total |
|---|---|---|---|
| 更新前 | data_0 | 3333 | 1333200 |
| **新ファイルを書いた直後（旧ファイルがまだある）** | data_0, data_1 | **6666** | **2666999** |
| 旧ファイルを消した後 | data_1 | 3333 | 1333799 |

（この環境で実際に得た値です。）

新ファイルを書いてから旧ファイルを消すまでの間、**同じデータが二重に数えられました**。本番のクエリがこの瞬間に走れば、売上が倍になったレポートが出てしまいます。最後の合計が`1333799`なのは、`400→999`の差分`+599`が正しく反映されたためです。

::: details 確認していないこと
ここで見たのは「更新の途中で二重に見える」という現象です。③（ファイル数が増えたときの一覧取得の遅さ）は、今回のローカルファイルでは再現していません。オブジェクトストレージでの実測は、後の章で扱います。
:::

## 1.4 他に取り得る手段

この問題に対して、業界は次のような答えを出してきました。

| 手段 | どう解決するか |
|---|---|
| Hiveテーブル（従来型） | フォルダ＋メタストア（テーブル名とフォルダ位置の対応）。上の①〜⑤はほぼそのまま残る |
| Delta Lake | フォルダ内のトランザクションログ（`_delta_log`）に、どのファイルが有効かを記録する |
| Apache Hudi | 「タイムライン」でコミットを管理し、更新に強い設計を持つ |
| **Apache Iceberg** | **メタデータのツリーで、テーブルに含まれるファイルを管理する。カタログが「今の版」の指し示しを担当する** |

どれも「フォルダの中身がテーブル」という前提をやめ、**テーブルに含まれるファイルを、メタデータとして別に記録する**点で共通しています。違いは、そのメタデータの持ち方と、周辺エコシステム（どのエンジンから読み書きできるか）です。

## 1.5 Icebergの答え：「テーブル」を定義し直す

Icebergは、テーブルの定義そのものを変えました。

> **テーブル ＝ フォルダの中身 ではなく、メタデータが記録している「ファイルの一覧」**

これで、①〜⑤の問題は次のように対処できます（詳しくは以降の章で扱います）。

| 問題 | Icebergの対処 | 章 |
|---|---|---|
| ① 1行のためにファイルごと書き直し | 変更分を別の「delete file」で表現でき、書き直しを避けられる場合がある | 4 |
| ② 書き込み途中が見える | 「今の版」をカタログが1点で切り替える。読み手は常に、古い版か新しい版のどちらかしか見えない | 2 |
| ③ `ls`が遅い | ファイル一覧はメタデータが持つので、`ls`しない | 2 |
| ④ スキーマの解釈がずれる | 列に固有のIDを振り、名前ではなくIDで管理する | 3 |
| ⑤ パーティションがフォルダ名の約束事 | パーティションの定義もメタデータが持つので、クエリ側が知らなくてよい | 4 |

## 1.6 既に知っているものでいうと何に近いか

| Icebergの要素 | 近いもの |
|---|---|
| snapshot（ある時点のテーブルの版） | gitのコミット |
| カタログ（今の版を指す1点） | gitのブランチ参照（HEAD） |
| manifest（ファイル一覧＋統計） | Snowflakeのマイクロパーティションのメタデータ（各パーティションのmin/maxを持ち、不要なものを読み飛ばす） |
| メタデータで版を管理する考え方 | DBのトランザクションログ／MVCC |

## 1.7 設計時に決めること

::: info Icebergを選ぶ判断の材料
次の要件が**1つでもある**なら、Icebergを検討する価値があります。

- 行の更新・削除・MERGEが要る（訂正、CDC、GDPRの削除要求など）
- 複数のエンジン（Spark / Flink / Trino / Snowflake / DuckDB など）から同じテーブルを読み書きしたい
- 過去のある時点の状態を、あとから再現したい（監査、再学習データの再現など）
- ファイル数が非常に多く、一覧取得やパーティション設計が問題になっている

**逆に、次のような場合は、Parquet＋パーティションのままで十分な可能性が高い**です。

- 追記のみで、更新・削除がほぼ無い
- 読み手が1種類のエンジンに決まっていて、規模も小さい
- チームにメタデータ（カタログ）を運用する余力が無い
:::

## 1.8 まとめ

- 従来のデータレイクは「フォルダ＝テーブル」で、更新・原子性・一覧取得・スキーマ・パーティションに構造的な弱さがあった
- Icebergは「テーブル＝メタデータが記録するファイルの一覧」と定義し直して解決した
- 次の章では、そのメタデータの層と、カタログが何をしているかを、実際にファイルを開いて確認します
